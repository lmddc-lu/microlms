# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Reusable micro-LMS engine, distributed as the pip package `microlms-core` but imported as `microlms` (mapped via `[tool.uv.build-backend] module-name` in pyproject.toml). Client projects install a tagged release, call `create_app()` with their own backends, and mount extra routers on top. This repo contains only the shared core; client repos are thin shells around it.

## Commands

```sh
uv sync                                # install deps (editable install of the package)
uv run pytest                          # run tests (needs Docker, see tests/conftest.py)
uv run pytest tests/test_courses.py -k <name>   # run a single test
uv run ruff check                      # lint (add --fix to auto-fix)
uv run ruff format                     # format code
uv run uvicorn main:app --reload       # dev server (needs .env, see .env.example)
uv run alembic upgrade heads           # apply migrations (needs MICROLMS_DATABASE_URL)
uv run alembic revision --autogenerate -m "msg" --head core@head   # new core migration
uv build                               # build sdist + wheel into dist/
```

Configuration comes from `MICROLMS_`-prefixed environment variables or `.env` (see `src/microlms/config.py`). `main.py` is a dev-only entrypoint for working on the core itself; client projects never use it.

## Architecture

The single supported entry point is `create_app(settings, engine, auth, storage, hooks, routers, modules, schedules, access_policy)` in `src/microlms/app.py`. Those nine parameters are the entire *customization* surface for client projects; anything that does not fit one of them is a core feature, not a client patch. The client builds the `engine` with `microlms.create_db_engine` and shares it with its own database work (hooks, periodic tasks) through `microlms.create_session_factory`, so a process holds a single connection pool; standalone scripts with no app build their own with the same two helpers (defined in `db/base.py`, re-exported as public API). Client routers mounted on the returned app may additionally *consume* two public read/call surfaces: `microlms.api.deps` (request-scoped wiring, permission checks, and the shared authorization loaders `get_user_in_scope`/`get_course_in_scope`/`get_readable_course`/`list_readable_courses`/`get_activity_in_course`/`get_enrollment_for_launch` - a client router replacing a core router builds on these instead of re-implementing scope and visibility rules) and the `microlms.domain.*` service functions, models and error types. In every module, the supported names are exactly those its `__all__` lists; anything else is internal even without a leading underscore. `__all__` starts from what clients use and grows on request: adding a name is a non-breaking change, removing one is breaking, so a name goes in only when a client needs it, together with the models and error types its functions take, return or raise. Keep all of these contracts stable - clients are forbidden from importing or monkey-patching anything else.

Core routers (`users`, `orgs`, `courses`, `enrollments`, `audit`, registry in `api/__init__.py`) are selected via the `routers` parameter. Any subset composes, and there is deliberately no inter-router dependency validation: dependencies are on data and domain services (always present), not on the router that ships as the default HTTP surface for them - a client may deselect a core router and mount its own replacement built on `microlms.domain` (adding the services it needs to their modules' `__all__`). The invariant that makes this safe: a router depends only on `domain/` and `api/deps.py`, never on another router. Never break it.

Authorization is permission-based and modelled on Kubernetes RBAC (`authz.py`): every core endpoint checks one specific `Permission` value (dot-separated strings named resource-first, e.g. `lms.user.edit`, `lms.course.publish`), never a role name. Roles are free-form string labels; the `AccessPolicy(roles, assign_permissions)` passed to `create_app` maps each label to a frozenset of concrete permission strings (no wildcards, no deny rules), so a client composes its own role vocabulary. Pass `DEFAULT_ACCESS_POLICY` for the bundled roles. The `lms.` namespace holds only `Permission` members; `create_app` rejects wildcard grants and unknown `lms.` strings up front. Scope belongs to the assignment, like a Kubernetes role binding, and any role may be assigned at either scope: a platform assignment in `lms_user_role` (outside any organization, acts in every org) or an org assignment in `lms_org_membership(user_id, org_id, role)` (acts in that org only), so a user belongs to several organizations with a different role in each. Self-registered users join `Settings.registration_org_slug` (unset = self-registration refused) and xAPI guests join `Settings.xapi_guest_org_slug` (set together with `xapi_guest_role`). Self is never permission-gated (the `/me` endpoints); courses scope by their owning org (`lms_course.owner_org_id`, None = platform-owned). A user's permissions are kept per source (`GrantedPermissions(platform, orgs)`), queried with `holds_permission`/`has_platform_permission`/`orgs_granting`/`permissions_at` (effective permissions at a scope = platform grants plus that org's), and `ManagementScope.org_ids` is the set of organizations where the checked permission is granted (None = platform-wide), with the actor's `permissions` alongside. An org-scoped actor reaches a user sharing one of those organizations (`get_user_in_scope`), but account-wide actions (profile, activation, deletion, password, impersonation) need every organization of the user in reach (`get_account_in_scope`). Endpoints gate via `microlms.api.deps.require_scoped_permission(permission)` (org-scoped actions, returns the `ManagementScope`), `require_platform_permission(permission)` (platform-global resources: orgs, audit, xAPI administration, removing a user from an org or adding them to a new one, platform roles - refused unless a platform assignment grants the permission), or `require_permission(permission)` (scope-free gates: catalog access, client-defined strings); client routers gate their own permission strings with the same factories. No escalation, for every actor (Kubernetes' role binding restriction): assigning or revoking a role at a scope needs every permission of the role there (`can_bind`), and reading or acting on an account needs, at every scope compared, every permission the account holds there (`can_manage`, enforced by `deps.forbid_unmanageable_target`; listings drop such accounts). So a manager may make peers but never hand out more than they hold (the bundled manager cannot grant instructor, whose content import runs package scripts on the app origin), and a client keeps accounts out of every manager's reach by granting them a permission managers lack. A role listed in `AccessPolicy.assign_permissions` also needs its assign permission, which the role itself does not grant, to be assigned or to have its holders acted on (`permissions_to_manage` folds it into what managing an account requires), so a client keeps a role out of its own holders' reach (managers who must not appoint or manage fellow managers). `GET /users/me/assignable-roles?org_id=` lists the roles the rule lets the current user assign there.

Extension points are protocols, each with a bundled default implementation:

- `auth/base.py` - `AuthBackend`: `authenticate(session, request)` per request, plus an optional backend-specific login router mounted under `/auth`, plus `openapi_security()` describing the credential scheme for the OpenAPI docs (create_app attaches it to the operations that resolve the current user). The backend owns credential extraction from the request (the `bearer_token` helper covers Authorization-header tokens), so cookie or assertion transports fit without core changes. Bundled backends: `AnonymousAuthBackend` (uuid4 tokens, working), `JwtAuthBackend` (`auth/jwt.py`, RFC 6749 token endpoint with the password and refresh token grants, rotated refresh tokens with reuse detection and RFC 7009 revocation (`domain/refresh_tokens.py`), browser session endpoints carrying the refresh token in an HttpOnly cookie, Argon2-hashed passwords and a client-supplied `PasswordPolicy` checked wherever a password is set, behind the `jwt` extra, working; it logs users in by their `lms_user.email`, a plain optional profile field, and keeps only the password and lockout state in `lms_password_credential` (`domain/password_credentials.py`)), `OidcAuthBackend` (`auth/oidc.py`, behind the `oidc` extra, working: OpenID Connect authorization code flow with PKCE through authlib against an external provider (`OidcProvider` connector), users known by issuer + `sub` in `lms_oidc_identity` (`domain/oidc_identities.py`), name, email and roles replaced from the provider's claims and mapped groups at every sign-in), and `LocalAuthBackend` (a stub - not implemented). The JWT and OIDC backends end a sign-in with the same LMS session (signed access token, rotated refresh tokens, browser session cookie endpoints), shared in the internal `auth/sessions.py`.
- `storage/base.py` - `StorageBackend`: put/open_range/size/exists/delete; `open_range(key, start, length)` returns a read/close-only handle on a byte window, so an object store (S3, Azure Blob) serves it with a single ranged GET and no backend ever needs a seekable handle. `FilesystemStorage` is the working default. `api/serving.py` turns a stored object into a streaming HTTP response with single-range (`Range`/206) support - the content modules serve package files through it.
- `events.py` - `EventHooks`: typed frozen-dataclass events (no string-keyed bus). Domain services queue events on their session (`queue_event`); the transaction owner finishes with `commit_with_events(session, hooks)`, which commits and then dispatches the queued events, so events only ever fire for committed work. Hooks run outside that transaction; one that needs the database opens its own sessions on the shared engine.
- `scheduler.py` - `PeriodicTask(name, interval, run)`: periodic background tasks passed as `create_app(schedules=[...])`, run once at startup and then every interval inside the app lifespan. A Postgres advisory lock keyed on the task name collapses concurrent firings across processes; tasks must be idempotent. `run` executes in a worker thread, so blocking work is fine; database work opens sessions on the shared engine.

Layering: `domain/` holds ORM models and service functions with no HTTP concerns; `api/` holds routers and Pydantic schemas and translates domain errors (e.g. `CourseNotFoundError`) into `HTTPException` at the boundary. Request-scoped wiring lives in `api/deps.py`, which resolves everything from `app.state` (populated by `create_app` and its lifespan) - there are no module-level globals for engine or settings. Domain services enforce no authorization, record no audit, and never commit: they `flush()` and queue their events, so several services compose into one atomic transaction. The transaction owner ends it - in core routers that is `AuditRecorder.record` (audit entry + commit + event dispatch in one step), in non-audited endpoints and client code an explicit `commit_with_events(session, hooks)`. Deliberate exceptions that commit themselves, documented in their docstrings: login lockout bookkeeping (`start_login_attempt`/`clear_login_failures`), the refresh token reuse revocation (committed by the token endpoint before it refuses the request), `provision_external_user` (concurrent-provisioning reconciliation), the xapi key `use_active_key` stamp, the lti `record_client_assertion` replay check, and the scorm/cmi5 runtime flows that persist state between LRS calls.

Content modules live in `modules/`, one self-contained package each exposing `build_router()`. `scorm` (SCORM 1.2 and 2004; the player normalizes both into one runtime payload), `cmi5` and `h5p` are implemented: they import a package as one language variant of a course activity (`domain/activities.py`: a course is an ordered list of activities, each with one package per language), play its content in the browser, keep all xAPI traffic to the LRS server-side (LRS credentials never reach the client), replace a variant's package in place (`PUT /{module}/variants/{variant_id}/package`: the variant and the activity progress recorded through it are kept, the module's runtime state is reset, and each package lives under its own `{module}/{variant_id}-{random}` storage prefix so the old files are deleted only after the commit), report the variant satisfied when the package is (`record_variant_satisfied`) - an activity is satisfied through any one of its language variants, and the enrollment completes once every activity of the course is - and stamp every launch on its activity (`record_activity_launched`, called from the launch endpoint before the module commits its launch state), which the activities listing exposes as `last_launched_at`; scorm and cmi5 also record the progress measure their content reports (`record_activity_progress_measure`, exposed as `progress_measure` and rolled up into the enrollment's `progress`), and scorm announces every runtime commit with its `suspend_data` (`ScormRuntimeCommitted`) so a client can derive progress an authoring tool keeps only there. `h5p` plays `.h5p` packages exported with their libraries bundled (authored externally, e.g. with Lumi - no in-browser authoring) via the vendored h5p-standalone player (`modules/h5p/assets/`, MIT, bundling the GPL-3.0 H5P core runtime; see THIRD_PARTY_NOTICES.md); the player page forwards the xAPI statements the content emits in the browser to the runtime endpoint, which stamps the canonical actor, registration and the activity IRI minted at import before forwarding to the LRS. Each module sits behind its own extra (`scorm`, `cmi5`, `h5p`) and needs the LRS settings (`lrs_url`, `lrs_api_key`, `lrs_api_secret`); the shared LRS client is `lrs.py`. `lti` is the platform side of LTI 1.3 (behind the `lti` extra, needs the LRS settings like the other content modules): a registered tool (`lms_lti_tool`, platform-reach `lms.lti.tools.manage`) is placed in a course as a resource link variant with one declarative line item; a launch runs the OIDC third-party initiated login, binding the learner through a single-use `lti_message_hint` (the browser carries no API credential), and posts an `id_token` signed with `Settings.lti_private_key`; the tool reports back through the AGS score service with an access token bought by a signed client assertion, and a `Completed` score satisfies the variant. The tool keeps the learner's interactions to itself, so the platform records what it sees in the LRS (`modules/lti/statements.py`): `launched` when it signs the launch, `completed`/`scored` when a score arrives, against the stable IRI `urn:microlms:lti:<resource_link_id>`; an applied score is posted before the commit, so an LRS failure refuses the score and the tool retries it. Modules are registered in `modules/__init__.py` and mounted only when the client lists them in `create_app(modules=[...])`.

## Database and migrations

- SQLAlchemy 2.0 style (`DeclarativeBase`, `Mapped`/`mapped_column`), pinned `<2.1`. Constraint names come from the naming convention on `Base.metadata` in `db/base.py`; never name constraints manually.
- Core tables are prefixed `lms_`. Client projects may reference them by foreign key but never alter them; client-specific data goes in client-owned satellite tables.
- Migrations ship inside the package (`src/microlms/db/migrations/`) as an Alembic chain with branch label `core`. Client projects add `microlms:db/migrations/versions` to their own `version_locations` and run `alembic upgrade heads` to apply both chains (documented in README.md, verified to work).
- New models must be imported in `db/migrations/env.py` so autogenerate sees them.

## Conventions

- New third-party dependencies for optional features belong in `[project.optional-dependencies]` extras, not core dependencies. Dev-only tools go in the `dev` dependency group.
- `tests/` holds end-to-end smoke tests through the public API, one file per feature (`test_enrollments.py`, `test_authz.py`, `test_scorm.py`, ...), with shared out-of-band seeding, `RecordingHooks`, `FakeLrs` and package builders in `tests/helpers.py`. Extend the file of the feature rather than adding narrow unit tests; a new feature gets its own file. Tests run on PostgreSQL in a testcontainers `postgres:17-alpine` (`tests/conftest.py`): the schema comes from `alembic upgrade heads` into a template database each test clones through the `database_url` fixture, and `test_migrations_match_models` fails when the models declare something no migration creates.
